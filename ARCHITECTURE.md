# Architecture: transparent LAN proxy → mitmproxy in a container (macOS)

Why and how it works. Installation and usage: [README.md](README.md); problems encountered during construction: [HISTORY.md](HISTORY.md).

## Goal

Intercept the HTTP/HTTPS traffic of devices connected to the Mac's physical LAN, routing it to `mitmproxy` running inside a Linux VM managed by Apple `container`. This architecture enables transparent proxying of the LAN.

The same container also intercepts the traffic **of the Mac itself**, only towards a list of chosen domains ([mac-domains.txt](mac-domains.txt)), even when the Mac is not connected to the LAN (`en7`): section 10.

## Why this approach

- The Mac is managed via MDM with **Digital Guardian** (`com.digitalguardian.webproxy`, Network Extension) and **BeyondTrust** (Endpoint Security + Privilege Management), plus **Microsoft Defender**.
- The **macOS Application Firewall** is centrally managed ("Firewall settings cannot be modified from command line on managed Mac computers").
- Traffic **forwarded/routed** by the kernel (not generated by a host process) does not go through the same per-process filters — hence the idea of moving mitmproxy into a Linux VM (`container`), which from the Mac's point of view is "another host" on the network, not a monitored local process.
- Direct bridging of `container` to a physical interface (e.g. `en7`) is **not available** in the stable release (Apple PR `#1622` still open) — so the container stays on the `default` network of `container` (vmnet NAT, `192.168.64.0/24`), reached by the Mac through explicit routing via `pf`.

## Network interfaces

| Interface | Role | Subnet |
|---|---|---|
| `en0` | WiFi, to the Internet | dynamic (`192.168.1.0/24` home, `10.0.0.0/24` office) |
| `en7` | Physical LAN, test clients | `192.168.3.0/24`, Mac = `192.168.3.2`, router/AP = `192.168.3.1` |
| `bridge100` | vmnet bridge of the `container` `default` network | `192.168.64.0/24`, gateway (Mac) `192.168.64.1` |

The LAN router and access point are **the same device** (Wind-branded Zyxel, `192.168.3.1`). Its DHCP server does not allow setting a gateway other than itself, so it is configured as a **DHCP relay** to the Mac: the actual DHCP is done by `dnsmasq` in a container (section 6), which hands out the Mac (`192.168.3.2`) as gateway to the clients.

The containers use the `default` network: **no dedicated network is needed**. Subnet and gateway can be checked with:
```bash
container network inspect default | jq '.[0].status'
```
The bridge name (`bridge100`) is not guaranteed to be stable: the pf daemon (section 9) derives it at runtime from the route to the container IP.

### Configuration (`mitm.conf`)

The values in the table are those of this installation. For another Mac or another LAN, only [mitm.conf](mitm.conf) is edited:
- `LAN_IP`: static IP of the Mac on the LAN interface, with prefix (`192.168.3.2/24`);
- `ROUTER_IP`: the router acting as DHCP relay to the Mac;
- `DHCP_FIRST`, `DHCP_LAST`, `DHCP_LEASE`: lease range and duration.

Everything else is derived at runtime, and follows network changes:
- **WAN** (`en0` here): interface of the default route. When switching from WiFi to Ethernet, or from home to office, NAT and the Mac traffic rules follow the new interface;
- **LAN interface** (`en7` here): the one that has `LAN_IP`. If it is missing (cable unplugged) the daemon omits the LAN rules and adds them within 60s of it appearing;
- **container bridge and subnet**: from the route to the container IP (daemon) and from the default interface inside the container (`entrypoint.sh`).

`mitm.conf` is read by `./mitm start dhcp` (generates `dhcp/lan.conf` for `dnsmasq`) and by the root daemon, which uses a copy in `/usr/local/etc/mitm.conf` (installed by `./mitm install`: the daemon does not read user-writable configuration). The file is never executed, only read line by line (`KEY=value`). After a change, `./mitm install` is enough: it updates the daemon's copy, and the DHCP LaunchAgent, once reinstalled, regenerates `dhcp/lan.conf` and restarts `dnsmasq`.
`./mitm start dhcp` and `./mitm status` warn if the values in the project file and in the daemon's copy differ.

## Installation

Procedure in [README.md](README.md#installation). `./mitm install` runs the root part ([daemon/install.sh](daemon/install.sh)) with a single sudo: the `com.mitm.pf` LaunchDaemon and the copy of `mitm.conf` (section 9), IP forwarding (section 1), the `.test` DNS domain of `container` (section 7). The rest without privileges: `container system start`, build of the images if missing, LaunchAgents (section 9). `./mitm uninstall` removes agents, daemon, pf rules and state files, and leaves IP forwarding and the `.test` domain, which may be useful for other things too.

## Traffic flow

```
LAN client (192.168.3.x) ──en7──▶ Mac pf: route-to (bridge100 <IP_CONTAINER>)   [dst IP unchanged]
                                       │
                                       ▼
                     container: iptables PREROUTING REDIRECT → :7070 (mitmproxy/mitmweb transparent)
                                       │  SO_ORIGINAL_DST → original destination
                                       ▼
                     mitmproxy ──▶ gateway 192.168.64.1 ──▶ NAT vmnet ──en0──▶ Internet

other LAN traffic (non-HTTP/S) ──en7──▶ Mac: nat on en0 (anchor com.apple/100.mitm.nat) ──▶ Internet

Mac traffic (browser) to <mitm_local> (IPs of the chosen domains), TCP 80/443:
  Mac ──out en0──▶ pf: route-to (bridge100 <IP_CONTAINER>)   [src IP of en0, dst unchanged]
                                       ▼
                     container: iptables REDIRECT → :7070 ──▶ mitmproxy ──▶ 192.168.64.1
                                       ▼
                     Mac: in bridge100, tag MITM_VM ──▶ nat on en0 ──▶ out en0 (tagged: no route-to) ──▶ Internet

DNS:
client ──UDP/TCP 53 → 192.168.3.2──en7──▶ Mac pf: rdr (anchor com.apple/100.mitm.dhcp) → <IP_DHCP>:53
                                              ▼
                     container mitm-dhcp (dnsmasq, cache) ──▶ 192.168.64.1 (Mac resolver via vmnet)
                                              ──▶ current DNS servers of the Mac (those of en0)

DHCP:
client ──broadcast──▶ router 192.168.3.1 (relay, giaddr=192.168.3.1)
                          │ unicast UDP → 192.168.3.2:67
                          ▼
                     Mac pf: rdr (anchor com.apple/100.mitm.dhcp) → <IP_DHCP>:67
                          ▼
                     container mitm-dhcp (dnsmasq) ──reply──▶ Mac (src rewritten to 192.168.3.2) ──▶ router ──▶ client
                     offers: IP 192.168.3.100–199, gateway 192.168.3.2, DNS 192.168.3.2, server-id 192.168.3.1
```

The container's replies to `192.168.3.x` go back to the Mac via the gateway `192.168.64.1` and are forwarded on `en7`: pf states on macOS are *floating*, so the state created on `en7` also covers the return path on `bridge100`.

For DHCP an `rdr` is enough (unlike mitmproxy, `dnsmasq` does not need the original destination). The packet is forwarded by the kernel to the container, not delivered to a Mac process, so the Application Firewall does not get involved (same principle as `route-to`). The rule is restricted to `on en7 from 192.168.3.1`: vmnet's internal DHCP on `bridge100` is not touched.

DNS follows the same scheme: clients query the Mac (`192.168.3.2:53`), pf does an `rdr` to the **same `dnsmasq` instance** as DHCP. A `dnsmasq` installed with brew on the Mac would receive nothing on port 53 (Application Firewall, like mitmproxy). `dnsmasq` forwards queries to the resolver in its own `/etc/resolv.conf` (`192.168.64.1`, the Mac's DNS proxy exposed by vmnet), which uses the Mac's current DNS servers, i.e. those received on `en0`: no public servers (`1.1.1.1` is not reachable on every network) and nothing to reconfigure when moving from home to office.

## Components

### 1. macOS — IP forwarding

The Mac acts as gateway for LAN clients: `./mitm install` (section 9) enables it immediately (`sysctl -w net.inet.ip.forwarding=1`) and across reboots (line in `/etc/sysctl.conf`).

### 2. macOS — `pf`: routing (not NAT) to the container

The key point of the architecture: traffic to port 80/443 is **not translated** (no `rdr`) but only **routed** (`route-to`) to the container IP, leaving the original destination address intact. This is required because mitmproxy in transparent mode on Linux retrieves the original destination via `getsockopt(SO_ORIGINAL_DST)`, which requires the NAT/redirect to happen **in the same kernel** where mitmproxy runs (so inside the container, not on macOS).

**`/etc/pf.conf` is not modified.** The rules live in child anchors of `com.apple`, `com.apple/100.mitm.*`, already reached by the `nat-anchor`, `rdr-anchor` and `anchor "com.apple/*"` lines of the system file. The children of an anchor with `*` are evaluated in name order (that is why Apple numbers them: `200.AirDrop`, `250.ApplicationFirewall`), so `100.*` comes before Apple's, and `com.apple/*` comes before the `com.apple.internet-sharing` anchors in the main ruleset. Verified with test rules on `bridge100`: the `block quick` and the `rdr` of `com.apple/100.*` take precedence over those of `com.apple/300.*`. A `quick` in a child anchor ends evaluation of the whole ruleset, as in the main ruleset. The children survive a reload of `com.apple` (verified); a full reload of `/etc/pf.conf` reloads `com.apple` from the file in the same way, so it should not touch them (not tested, to avoid removing the `InternetSharing` anchors). As a result:
- no manual setup of `/etc/pf.conf` (macOS updates may restore it);
- no need for a full reload, which removes the `InternetSharing` anchors ([history](HISTORY.md), item 13).

The anchors are generated and loaded by the `com.mitm.pf` daemon (section 9); the rule templates are in [daemon/mitm-pf-apply](daemon/mitm-pf-apply), the generated files in `/etc/pf.anchors/mitm.*`. Since they are not loaded by `/etc/pf.conf`, the anchors are empty at boot: the daemon loads them (`RunAtLoad`).
- `com.apple/100.mitm.nat` (always active): NAT to the Internet for the rest of the LAN traffic, non-HTTP/S, and for container egress:
  ```
  nat on en0 inet from 192.168.3.0/24 to any -> (en0)
  nat on en0 inet from 192.168.64.0/24 to any -> (en0)
  ```
  The second line is needed if the anchors of `InternetSharing` (started by `container-network-vmnet`) are missing; it normally does the NAT of the container network by inserting its own pf anchors into the main ruleset at runtime: a full reload (`pfctl -f /etc/pf.conf`, done by some system service or by hand) removes them, and from then on the containers can no longer reach the Internet (mitmproxy receives the client connections but times out towards the servers). With our rule, egress does not depend on them; if they are present, the first matching rule applies, no double NAT.
- `com.apple/100.mitm.route`: `route-to (bridge100 <IP_CONTAINER>)` of TCP 80/443 coming in on `en7` from the LAN. The interface in the `route-to` is the **vmnet bridge** (`bridge100`), not `en7`. It also contains the rules for the Mac's traffic to the `<mitm_local>` table (section 10).
- `com.apple/100.mitm.dhcp`: `rdr` to `<IP_DHCP>` of the DHCP relay (UDP 67 from `192.168.3.1` to `192.168.3.2`) and of DNS queries (UDP/TCP 53 from the LAN to `192.168.3.2`). DNS is restricted to queries **to the Mac**: a client with manually configured DNS (e.g. `8.8.8.8`) goes out via NAT as before.

DHCP (and DNS, served by the same container) and mitmproxy each have their own anchor and their own lifecycle (sections 3 and 8): `./mitm stop` removes interception without interrupting DHCP.

**pf on macOS is not enabled by default**: `pfctl -f` loads the rules but does not activate them. The daemon enables it (`pfctl -E`) if needed.

The daemon reloads **only the single anchor** (`pfctl -a <anchor> -f ...`), never the whole `/etc/pf.conf`: reloading the main ruleset removes the anchors inserted dynamically by system services (see the comment at the top of `/etc/pf.conf`).

Previous version: `com.mitm.*` anchors declared in a modified copy of `/etc/pf.conf`. `daemon/install.sh` removes those lines (backup in `/etc/pf.conf.mitm-bak`) and flushes the old anchors without a full reload; the empty references left in the main ruleset disappear at reboot.

### 3. The `mitm` command

A single command, [mitm](mitm), for start, stop and diagnostics:
```
./mitm start [dhcp]            start DHCP and mitmproxy (with dhcp: DHCP only)
./mitm stop [dhcp|all] [--rm]  stop mitmproxy (dhcp: DHCP only; all: both)
./mitm status                  status of containers, pf rules, daemon and agents
./mitm open                    mitmproxy interface (web UI in the browser, or console)
./mitm attach                  mitmproxy console (tmux)
./mitm mock                    mock dashboard in the browser (section 11)
./mitm logs [dhcp|pf] [-f]     logs of mitmproxy, dnsmasq or the pf daemon
./mitm build [proxy|dhcp]      build the images (default: both)
```

The container IP changes at every restart (there is no flag to pin it — `container run --network` only supports `mac`/`mtu`, not `ip`): `start` reads the current IP and has the corresponding pf anchor regenerated.

DHCP and mitmproxy have **separate lifecycles**, with a one-way dependency:
- `start dhcp` is **standalone**: it only manages `mitm-dhcp` and the `com.apple/100.mitm.dhcp` anchor, and does not touch mitmproxy. With only DHCP active, clients have the Mac as gateway and browse via NAT, without interception.
- `start` **depends on DHCP**: it first runs `start dhcp`, then manages `mitmproxy.test` and the `com.apple/100.mitm.route` anchor.

`start` is **idempotent** and can be rerun at any time:
- container **does not exist** → builds the image if missing, then creates the container with `container run` (for mitmproxy this is the only moment `MITM_UI`, default `console`, and `MITM_WEB_PASSWORD`, default `password`, are read);
- container **stopped** → `container start`. If the start fails (e.g. project moved: the volumes are registered with the absolute path, section 9) the command stops and says to recreate it, instead of trying to create another one with the same name;
- container **running** → no action on the container.

Then it waits for the IP to be assigned (up to ~10s), and for the daemon to apply the rule. `start dhcp` first generates `dhcp/lan.conf` from `mitm.conf`, and restarts `mitm-dhcp` if it changed (`dnsmasq` reads its configuration only at startup). If no interface has `LAN_IP` it does not wait for the rules: the daemon generates them when the LAN is connected.

It must be run **without sudo** (`container run/inspect` require the user session) and asks for no privileges: instead of writing the anchors, it writes the current IP to a state file in `/usr/local/var/mitm-pf/` (`dhcp` / `route`) and waits (up to ~10s) for the root LaunchDaemon `com.mitm.pf` to apply the rule (section 9). It changes to the project directory (even through a symbolic link, e.g. `ln -s "$PWD/mitm" /usr/local/bin/mitm`), so the relative volumes (`./mitmproxy`, `./export`, `./dhcp`) work from whatever directory it is run.

`status` requires no privileges: it reads the containers, the state files and the files generated by the daemon (`/etc/pf.anchors/mitm.*`, world-readable), and reports inconsistencies, for example a pf rule routing to a stopped container (LAN clients' HTTP/HTTPS into the void), an outdated daemon copy of `mitm.conf`, a failed LaunchAgent or IP forwarding turned off.

### 4. Container — image (`Containerfile`)

Base `python:3.13-slim-bookworm` and **not** `debian:bookworm-slim`: Debian bookworm has Python 3.11, and recent mitmproxy versions require Python ≥ 3.12 (since 11.1). With `pip install mitmproxy` on bookworm you silently get **11.0.2**, which lacks the `web_password` option (mitmweb exits with an error) and the web UI protection introduced in later versions. The version is pinned for reproducible builds.

File: [Containerfile](Containerfile). `container build` finds it automatically (otherwise `-f Containerfile`). It also installs [mac-editor.sh](mac-editor.sh) as `MITMPROXY_EDITOR` (section 7, *Editing on the Mac*): the image has no editor.

### 5. Container — entrypoint (`entrypoint.sh`)

File: [entrypoint.sh](entrypoint.sh): sets up the `iptables` REDIRECT (80/443 → 7070) and launches mitmproxy in transparent mode, with the interface chosen by `MITM_UI` (section 7):
- `console` (default): `mitmproxy` (text interface) in a `tmux` session named `mitm`;
- `web`: `mitmweb`, web UI on `:8081`.

The two modes are alternatives: only one process can listen on `7070`, and mitmproxy does not offer console and web UI together.

Critical points:
- **`iptables -t nat -F PREROUTING` before re-adding the rules**, to avoid duplicates at every restart.
- **Match `! -s <container network> -m addrtype ! --dst-type LOCAL`**: the REDIRECT applies to LAN clients (`192.168.3.0/24`) and to the Mac (WAN IP, which changes between home and office: section 10), not to the container network nor to direct connections to the container. The container network (`192.168.64.0/24`) is derived at startup from the interface of the container's default route (`ip -4 route`), and is written to `container logs mitmproxy.test`. Previously the match was `-s 192.168.3.0/24`: without a source filter, a total timeout of container egress to the Internet had been observed ([history](HISTORY.md), item 8), probably actually caused by the removed NAT anchors ([history](HISTORY.md), item 13). **Still to be verified** that the new match does not reproduce the problem. A change to `entrypoint.sh` requires `container build` and recreating the container (`./mitm build proxy && ./mitm stop --rm && ./mitm start`).
- **`tini` as PID 1** (via `ENTRYPOINT`) and **mitmproxy/mitmweb in a `while` loop**: it is a child process that can be killed/restarted without stopping the container. Without the loop, when mitmweb exits the entrypoint terminates and the container with it.
- **Console: two loops**. The one inside the `tmux` session restarts `mitmproxy` after an exit (`q`) without closing the session, so whoever is attached immediately sees the new instance. The outer one, in the entrypoint, recreates the session if it is closed (`tmux kill-session`) and keeps the container alive: `tmux new-session -d` returns immediately, and without the loop the entrypoint would terminate. In console mode `container logs mitmproxy.test` does not show mitmproxy's output (it is in the `tmux` session, events with `E`).
- **Current directory `/export`** (volume `./export`, section 7): relative paths of commands that write to disk end up there.
- **Mock dashboard started in the background** (`python3 /mockui/server.py`, supervised by a `while` loop like mitmproxy), before the two `MITM_UI` branches, so it runs in both: section 11. `MITM_VM_NET` is exported for it — the container network is already computed above for the `iptables` rule.
- **`/edit` emptied at startup** (volume `./edit`, section 7): leftovers of edits interrupted by a container stop.
- **`block_global=false`**: `block_global` blocks connections from **clients** with a public IP (it does not concern the destination). LAN clients `192.168.3.x` are private, so it is not strictly needed; it is kept to avoid surprises if a client shows up with a non-private IP.
- **Web UI password** (only `MITM_UI=web`) **from an environment variable** (`MITM_WEB_PASSWORD`, passed with `container run -e`), not written into the image. `./mitm start` always passes it, defaulting to `password` if not set. If the variable were missing entirely (container started by hand), mitmweb generates a random token printed in the logs (`container logs mitmproxy.test`). The web UI is also reachable from LAN clients (the Mac forwards `192.168.3.0/24` → `192.168.64.0/24`): with the default password anyone on the LAN can access it.

### 6. DHCP and DNS container (`dhcp/`)

Separate `mitm-dhcp` container with `dnsmasq`, acting as both DHCP and DNS (with cache) for the LAN: reached by the router's relay and by the clients' DNS queries to the Mac through pf's `rdr` rules (see *Traffic flow*). It is separate from `mitmproxy.test` because it has a different lifecycle (`./mitm start dhcp` / `./mitm stop dhcp`), independent of mitmproxy: `./mitm stop` stops interception but leaves DHCP active, so clients keep receiving/renewing their lease and browse via the Mac's NAT.

Discarded alternatives:
- **DHCP/DNS server on macOS** (`dnsmasq`/`kea` from brew): a process listening on the Mac, blocked by the Application Firewall like mitmproxy ([history](HISTORY.md), item 1). Also tried for DNS: port 53 receives nothing.
- **Fixed public DNS servers** (`1.1.1.1`, `1.0.0.1`): not reachable on every network (e.g. corporate networks that only allow their own DNS).
- **Upstream DNS read from `en0`** (`ipconfig getoption en0 domain_name_server`) and written to a `resolv-file` for `dnsmasq`: requires a job that follows network changes. The vmnet resolver (`192.168.64.1`) already follows them on its own, and also honours the Mac's full DNS configuration (per-domain resolvers, VPN).
- **macOS `bootpd`** (`/etc/bootpd.plist`): the same file is used by Internet Sharing/vmnet, risk of interfering with the container network.
- **Relay pointed directly at the container IP**: the IP changes at every restart, and the router would send the requests to its own gateway, not to the Mac.

Files: [dhcp/Containerfile](dhcp/Containerfile) and [dhcp/dnsmasq.conf](dhcp/dnsmasq.conf), which includes `dhcp/lan.conf` (range, gateway, DNS and `dhcp-proxy`), generated by `./mitm start dhcp` from `mitm.conf` and ignored by git. Configuration and leases live in the `/data` volume (`./dhcp` on the Mac): a change to `dnsmasq.conf` only requires `container stop/start mitm-dhcp`, not a rebuild. `dnsmasq` runs with `--user=root`, otherwise it drops privileges and cannot write the lease file in the volume.

Critical points:
- **Explicit netmask in `dhcp-range`**: for networks served via relay, `dnsmasq` cannot derive it from the local interfaces.
- **`dhcp-proxy=192.168.3.1`**: normally, after the first lease, the client renews via **unicast to the server-ID** (option 54), which would be the container IP — reachable only until it changes. With `dhcp-proxy` the server-ID is the relay address, and renewals also go router → Mac → container.
- **`dhcp-authoritative`**: `dnsmasq` is the only DHCP server on the LAN; it replies immediately even to clients that still hold a lease from the router's old DHCP, instead of ignoring them.
- **1h lease**: a gateway/DNS change reaches clients within ~30 min (T1).
- **Range `.100–.199`**: outside `.1` (router), `.2` (Mac) and the static IPs already in use (e.g. `.249`).
- **`--cap-add NET_ADMIN`** is mandatory here too: without it, `dnsmasq` exits at startup with `process is missing required capability NET_ADMIN`.
- **Persistent leases** in `./dhcp/dnsmasq.leases`: after a container restart `dnsmasq` does not reassign IPs already in use.
- **DNS without `port=0`**: port 53 is active. No `server=` directive: `dnsmasq` uses the `nameserver` from the container's `/etc/resolv.conf` (`192.168.64.1`, set by `container`), so even a subnet change of the `default` network requires no changes. At startup the log shows `using nameserver 192.168.64.1#53`.
- **Explicit `dns-server=192.168.3.2`**: without it, `dnsmasq` would offer its own IP as DNS (the container's, unreachable from clients and variable).
- **Queries from non-local subnets accepted**: queries come from `192.168.3.x`, which is not a container subnet. `dnsmasq` 2.90 launched directly (without Debian's init script) does not apply `--local-service`; if it did, the startup log would report `DNS service limited to local subnets`.

Router configuration (Zyxel): DHCP in **Relay** mode, server `192.168.3.2`. No other DHCP server must remain active on the LAN.

DHCP log: `./mitm logs dhcp` (to also see DNS queries, add `log-queries` to `dnsmasq.conf`).

DNS check, directly from the Mac (UDP; with `+tcp` for TCP):
```bash
dig @$(container inspect mitm-dhcp | jq -r '.[0].status.networks[0].ipv4Address' | cut -d/ -f1) example.com
```
This tests `dnsmasq` and its upstream, not the `rdr` of `192.168.3.2:53`: that must be verified from a LAN client.

### 7. mitmproxy container: interface, web UI and volumes

Usage (start, `./mitm open`, changing interface): [README.md](README.md#usage). The containers are on the `default` network (no `--network`).

Interface chosen with `MITM_UI`, read only when the container is created (to change it the container must be recreated, because `start` does not touch an existing container). `./mitm open` opens whichever one the container was created with (read from `container inspect`):
- `console` (default): `mitmproxy` in `tmux` (section 5). `./mitm open` and `./mitm attach` are `container exec -it mitmproxy.test tmux attach -t mitm`: no ssh, which is not needed and would expose one more port, to the LAN too.
- `web`: `mitmweb` on `:8081`, password from `MITM_WEB_PASSWORD` (default `password`). `./mitm open` opens `http://mitmproxy.test:8081/` in the default browser, without the password in the URL (`?token=`): it would end up in the browser history.

#### Editing on the Mac (console)

The console edits a part of a flow (body, URL, header cell, …) by writing it to a temporary file and running `$MITMPROXY_EDITOR <file>`, then reads the file back when the command exits; the external viewer (`v`) uses the same variable, with a read-only file. The image has no editor, and the editing should happen in a desktop application on the Mac: `MITMPROXY_EDITOR` (set in the `Containerfile`) is [mac-editor.sh](mac-editor.sh), which hands the file over to the Mac through the `./edit` volume:

```
mitmproxy ──/tmp/mitmproxyXXXX──▶ mac-editor: cp → /edit/mitmproxyXXXX, request /edit/mitmproxyXXXX.open (edit|view)
                                       │ ./edit (volume)
                                       ▼
          ./mitm open|attach (Mac, background, every 0.5s): claims the request (mv), open -a "$MITM_EDITOR" | open -t | open
                                       │ the user edits and saves on the Mac
                                       ▼
          mac-editor: Enter → /edit/mitmproxyXXXX → /tmp/mitmproxyXXXX, removes the copy ──▶ mitmproxy reads the file
```

- **The Mac side lives in `./mitm open`/`attach`**, as a background loop for the duration of the attach (killed on exit), not in a LaunchAgent: files are edited only from an attached terminal, the application (`MITM_EDITOR`) is read at every attach without recreating the container, and no throttling (a `WatchPaths` LaunchAgent starts at most every 10s). The loop writes nothing to the terminal (it would write over the console): an `open` error (e.g. application not found) goes back to the container in `<file>.error`, and `mac-editor` shows it. With several attached terminals, the `mv` of the request makes only one of them open the file.
- **End of editing = Enter in the terminal**, not the application closing: `open -a` returns immediately, and most applications stay open after closing the document. It works with any application; `d` + Enter discards the changes, without rewriting the original file. Ctrl-C must not be used: it would also reach mitmproxy, which is in the same foreground process group.
- **Without an attached `./mitm open`/`attach`** (e.g. `container exec … tmux attach` by hand) nobody takes the request within 3s: `mac-editor` says to open `edit/<file>` by hand, and the rest is the same.
- **Files replaced on the Mac invisible for ~1s**: many editors save atomically (new file + rename); through the volume, the container keeps seeing the old entry, already removed (`No such file or directory`) until the directory is listed again or ~1s has passed. Writes in place, and files written by the container, are visible immediately on the other side. `mac-editor` lists `/edit` before reading the file back, and retries for 5s; the copy into mitmproxy's file goes through a temporary file, so that a failed read does not empty the original.
- **Viewer** (read-only file, with the extension of the content type): opened with the default application for the type (`open`, or `open -t` if no application handles it), not with `MITM_EDITOR`; Enter returns to mitmproxy without reading anything back.
- The copies in `./edit` are removed after Enter, and at every container start; the `.open`/`.error` files never contain flow data. The directory is ignored by git.

After a Mac reboot the `container` services do not restart on their own (`apiserver is not running and not registered with launchd`): the `com.mitm.dhcp` LaunchAgent (section 9) starts them at login, together with DHCP. mitmproxy is restarted by hand with `./mitm start`.

#### Web UI from the Mac (`MITM_UI=web`): `http://mitmproxy.test:8081`

`container` includes a local DNS server (`container-apiserver`, listening on `127.0.0.1:2053`). `sudo container system dns create test` creates `/etc/resolver/containerization.test`, which tells macOS to resolve `*.test` names through that server. The name follows the container IP on its own: nothing to update after a restart.

The built-in DNS resolves **only containers whose name is `<name>.<domain>`**: that is why the mitmproxy container is called `mitmproxy.test` (`PROXY=mitmproxy.$DNS_DOMAIN` in `mitm`). A container named `mitm-proxy` is not resolved, neither as `mitm-proxy` nor as `mitm-proxy.test`, even if created with `--dns-domain test` (see [Mcrich23/Container-Compose#81](https://github.com/Mcrich23/Container-Compose/issues/81)).

`--dns-domain test` only sets the DNS *inside* the container (`/etc/resolv.conf` → `nameserver 192.168.64.1`, `domain test`); resolution of external names keeps working. For the name on the Mac only the container name matters.

The name works **only on the Mac**: the `container` DNS server answers on `127.0.0.1`, LAN clients cannot use it.

To check name resolution and the web UI from a terminal (without a password mitmweb answers `403` with the login page, with `?token=<password>` it answers `200`):
```bash
dscacheutil -q host -a name mitmproxy.test
curl -s -o /dev/null -w '%{http_code} %{remote_ip}\n' http://mitmproxy.test:8081/
```

To stop: `./mitm stop` (section 8).

Notes:
- `--cap-add NET_ADMIN` is **mandatory**: without this capability, `iptables` fails with `Permission denied (you must be root)` even though the process runs as root at the Linux user level (the default container has a reduced capability set).
- `--volume ./mitmproxy:/root/.mitmproxy` makes the container's mitmproxy configuration persistent, CA included. The path is relative to the project directory, and `./mitmproxy` must exist (otherwise `container run` fails with `path './mitmproxy' does not exist`). If permission errors show up, `chmod -R 777 ./mitmproxy` on the Mac.
- **Only the configuration** of `./mitmproxy` **is in git**: `config.yaml`, `keys.yaml`, `scripts/`. The files mitmproxy generates in the same directory are ignored and stay only on disk: the CA (`mitmproxy-ca.pem` and `mitmproxy-ca.p12` contain the **private key**, with which anyone can intercept the traffic of devices that have the CA installed), `mitmproxy-dhparam.pem`, `wireguard.conf` (private keys of the WireGuard mode) and `command_history`. They have also been removed from the repo history.
- **CA on another Mac**: without the CA files, on first start mitmproxy generates a **new** one, to be reinstalled on every device. To reuse the one already installed, copy it by hand (not via git) from the `mitmproxy/` directory of the old Mac, or from `~/.mitmproxy`: `mitmproxy-ca.pem`, `mitmproxy-ca.p12`, `mitmproxy-ca-cert.*`, `mitmproxy-dhparam.pem`.
- A dedicated directory prevents the container from loading the `~/.mitmproxy/config.yaml` used on the Mac (with its `ignore_hosts`, `ssl_insecure`, …). A `config.yaml` in `./mitmproxy`, if present, is loaded: command-line options (`mode`, `listen_port`, `web_port`, …) take precedence, everything else is applied. To avoid having two different values for the same option, those set by `entrypoint.sh` must not be repeated in `config.yaml`.
- `--volume ./export:/export`: mitmproxy's working directory, to get on the Mac the files saved by its commands, for example `:save.file @shown flows.mitm` (or `w`), `:export.file curl @focus request.sh`, `:cut.save @focus response.content body.bin`. Relative paths end up in `./export`; absolute ones (e.g. `/tmp/x`) stay in the container. Like `./mitmproxy`, the directory must exist: `./mitm start` creates it. The files appear on the Mac owned by the current user. It is ignored by git.
  A project folder is mounted rather than the Desktop: `~/Desktop` is protected by TCC (the access would be made by `container`'s virtualization process, and on a managed Mac the authorization may be denied by policy), and there is no need to give a root process that handles untrusted traffic write access to the whole Desktop. To keep it at hand: `ln -s "$PWD/export" ~/Desktop/mitm-export`.
- `--volume ./edit:/edit`: files being edited on the Mac (section 7, *Editing on the Mac*). It must exist too: `./mitm start` creates it.
- `--volume ./mocks:/mocks` and `--volume ./mockui:/mockui`: mock definitions and uploaded contents, and the dashboard that manages them (section 11). `./mocks` is created by `./mitm start` and ignored by git; `./mockui` is code, and is mounted instead of being copied into the image so it can be changed without a rebuild.
- `MITM_WEB_PASSWORD` in clear text is visible in `container inspect mitmproxy.test` and in the container's process list. To avoid this, `web_password` also accepts an argon2 hash (mitmweb itself suggests it at startup).

### 8. Stopping (`./mitm stop`)

`./mitm stop` **does not stop DHCP**: clients keep the Mac as gateway and browse via NAT, without interception. DHCP only: `./mitm stop dhcp`; everything: `./mitm stop all`.

Stopping just the container **is not enough**: the pf rule would stay active towards an IP that is no longer listening (with `route-to`, HTTP/HTTPS blocked for the whole LAN). For each service, `stop`:
- stops the container if it is running (with `--rm` it also removes it — needed to change interface, password or image);
- empties the state file; the `com.mitm.pf` daemon (section 9) then:
  - empties the generated file (`/etc/pf.anchors/mitm.route` or `mitm.dhcp`), on which the command waits for confirmation;
  - flushes the anchor in pf (`-F rules` for the `route-to`, `-F nat` for the `rdr`: `rdr` rules are translation rules, `-F rules` would not touch them);
  - kills the pf states tied to the old rule: for mitmproxy those of the LAN clients (`pfctl -k 192.168.3.0/24`, which also includes the DHCP relay states, recreated at the next packet), for DHCP/DNS those LAN → Mac (`pfctl -k 192.168.3.0/24 -k 192.168.3.2`: the router's relay and the clients' DNS queries).

After `./mitm stop dhcp` clients cannot renew their lease: if the Mac stops acting as gateway, the router must be put back in DHCP server mode.

Like `start`, it must be run **without sudo**. It can be rerun even if the containers are already stopped or do not exist.

To resume: `./mitm start` (also restarts DHCP if needed), or `./mitm start dhcp` for DHCP only.

`stop` deliberately leaves active:
- **pf**: `pfctl -d` is not used, as it would disable it system-wide (including macOS/MDM services that use it); with empty anchors pf has no effect on LAN traffic;
- **IP forwarding**: turning it off (`sudo sysctl -w net.inet.ip.forwarding=0`, and removing the line from `/etc/sysctl.conf` to make it permanent) cuts LAN clients off from the Internet.

### 9. pf rules without sudo and start at login (`daemon/`, `launchagent/`)

User scripts cannot update pf on their own (root is needed, with a BeyondTrust prompt at every `sudo`), and at login there is nobody to confirm a prompt. The privileged part is therefore split into a **root LaunchDaemon**, installed once:

```
user script ──writes IP────▶ /usr/local/var/mitm-pf/{route,dhcp}   (user)
                                   │ launchd WatchPaths
                                   ▼
                     com.mitm.pf (root): validates, regenerates /etc/pf.anchors/mitm.{nat,route,dhcp},
                                         pfctl -a com.apple/100.mitm.<x> -f|-F, pfctl -k, pfctl -E if needed
```

- **State files** (written with an atomic rename, so the daemon never reads a half-written file):
  - `route` → `<mitmproxy IP>` (empty = no interception; the daemon derives the bridge);
  - `dhcp` → `<dnsmasq IP>` (empty = no DHCP/DNS);
  - `domains` → copy of [mac-domains.txt](mac-domains.txt), written by `./mitm start` and by the `com.mitm.domains` LaunchAgent at every change of the file (section 10).
- **Validation**: the content is user-writable, so it is never executed or copied as is; the daemon only accepts IPv4 addresses and domain names (regex, at most 64) and generates the rule from a fixed template. Any other content empties the rule (or, for domains, is ignored).
- **Configuration and network**: it reads `LAN_IP` and `ROUTER_IP` from its own copy of `mitm.conf` (`/usr/local/etc/mitm.conf`, root:wheel) and at every run derives WAN, LAN interface and bridge (see *Configuration*). The detected network is logged when it changes.
- **Every 60s** (`StartInterval`) and **at every change of the system DNS** (`WatchPaths` on `/var/run/resolv.conf`, which changes with the network): the daemon regenerates the rules if the network has changed and, with interception active, re-resolves the domains and updates the `<mitm_local>` table; if nothing changes it does not touch pf.
- **Root script in `/usr/local/libexec/mitm-pf-apply`** (root:wheel, 755), not in the project directory: otherwise anyone who can write to the project could have code executed as root.
- **No unnecessary reloads**: the anchor is reloaded (and states killed) only if the rule changes.
- **At boot** (`RunAtLoad`): state files **older than the last boot** (`kern.boottime`) are ignored, so the rules of the previous session are flushed. This fixes the `route-to` to a nonexistent IP left behind after a reboot with mitmproxy active.
- Log: `/var/log/mitm-pf.log`.

Files: [daemon/mitm-pf-apply](daemon/mitm-pf-apply) (root script, contains the rule templates) and [daemon/com.mitm.pf.plist](daemon/com.mitm.pf.plist) (LaunchDaemon with `RunAtLoad`, and `WatchPaths` on the state directory and on `/var/run/resolv.conf`).

Installed with `./mitm install` (see *Installation*), which runs [daemon/install.sh](daemon/install.sh) with sudo: it copies the script to `/usr/local/libexec` and `mitm.conf` to `/usr/local/etc`, creates the state directory (owned by the user) and loads the daemon. It must be rerun after every change to `daemon/mitm-pf-apply` or `mitm.conf`: the daemon runs the installed copy, not the project file.

Check: `sudo launchctl print system/com.mitm.pf | grep -E 'state|last exit'`.

#### Starting DHCP at login (LaunchAgent `com.mitm.dhcp`)

The `container` services are launchd jobs of the **user session**: after a reboot they are not registered (`apiserver is not running and not registered with launchd`) and before login they cannot run. At every login the LaunchAgent runs `container system start` (idempotent: with the services already active it exits successfully) and then `./mitm start dhcp`. mitmproxy does **not** start at login: it is started by hand with `./mitm start`.

Definition in [launchagent/com.mitm.dhcp.plist](launchagent/com.mitm.dhcp.plist) (`container` is in `/usr/local/bin`, so the plist sets `PATH`, which is missing from launchd's default one). The project's plist contains no absolute paths: launchd does not expand `~` or `$HOME`, so `install.sh` replaces the placeholders `__PROJECT_DIR__` and `__HOME__` with the project directory and the user's home. If the project is moved, `./mitm install` must be rerun, and the containers recreated (`./mitm stop all --rm`, then `./mitm start`): the volumes (`./mitmproxy`, `./dhcp`) are registered with their absolute path at `container run` time, and `container start` fails with `mount source path '...' does not exist`.

#### Changes to `mac-domains.txt` applied on save (LaunchAgent `com.mitm.domains`)

The LaunchAgent has `WatchPaths` on [mac-domains.txt](mac-domains.txt): at every save it copies the file into the `domains` state (atomic rename), and the `com.mitm.pf` daemon, triggered by the change in the state directory, updates the `<mitm_local>` table (section 10). The watch fires both on in-place writes and on editors' atomic saves (new file + rename). launchd runs it at most every 10s (default `ThrottleInterval`): a change made shortly after another is applied with a few seconds' delay. With interception off the daemon ignores the list; `./mitm start` copies it at startup anyway.

The watch lives in the user session and not in the root daemon: this way the daemon does not need to know the project directory.

Definition in [launchagent/com.mitm.domains.plist](launchagent/com.mitm.domains.plist).

#### Installing the LaunchAgents

[launchagent/install.sh](launchagent/install.sh) installs (or, with `--remove`, removes) all the `com.mitm.*.plist` plists in `launchagent/`, as a normal user, without sudo. It is run by `./mitm install` and `./mitm uninstall`.

Logs: `~/Library/Logs/mitm-dhcp.log` and `~/Library/Logs/mitm-domains.log`. Status: `launchctl print gui/$(id -u)/com.mitm.dhcp | grep -E 'state|last exit'` (same for `com.mitm.domains`).

### 10. Mac traffic to chosen domains (`mac-domains.txt`)

The Mac's browser goes through mitmproxy only for the domains listed in [mac-domains.txt](mac-domains.txt), with or without the LAN: only the container and the WAN (default route) are needed. It is enabled and disabled together with LAN interception (`./mitm start` / `./mitm stop`). Changes to the list are applied when the file is saved, within a few seconds (LaunchAgent `com.mitm.domains`, section 9); without the LaunchAgent, rerunning `./mitm start` is enough.

Why a route is not enough (`route add -host example.it -interface bridge100`):
1. `-interface` treats the destination as directly attached to `bridge100`: ARP for the site's IP, nobody answers. The container would be needed as gateway.
2. Even with the gateway a loop is created: mitmproxy's connection to the same IP goes through the Mac, finds the same route and returns to the container. The routing table decides on the destination only.
3. The REDIRECT in the container applied only to `-s 192.168.3.0/24`.
4. A route applies to an IP, not to a domain, and CDNs use many IPs that change.

pf rules (in `com.apple/100.mitm.route`, generated by the daemon, template in [daemon/mitm-pf-apply](daemon/mitm-pf-apply)):
```
table <mitm_local> persist
pass in on bridge100 inet proto tcp from <IP_CONTAINER> to any port { 80, 443 } tag MITM_VM keep state
pass out quick on en0 route-to (bridge100 <IP_CONTAINER>) inet proto tcp from (en0) to <mitm_local> port { 80, 443 } ! tagged MITM_VM keep state
block return out quick on en0 inet6 proto tcp from any to <mitm_local> port { 80, 443 }
block return out quick on en0 proto udp from any to <mitm_local> port 443
```
- **Outbound `route-to`** on the WAN (`en0` in the examples): as for the LAN, the packet is not translated, the REDIRECT happens in the container (`SO_ORIGINAL_DST`). The source stays the IP of `en0`: the container replies via `192.168.64.1` and the (floating) pf state covers the return path on `bridge100`.
- **Anti-loop tag**: outbound filter rules see addresses **after NAT**, so mitmproxy's connections to the Internet also have source `(en0)` on `en0`. They are tagged `MITM_VM` when entering from `bridge100` and excluded from the `route-to` with `! tagged`. The tag is *sticky* (it stays even if a later rule decides): the rule that applies it is not `quick` and does not override the `com.apple/*` rules on `bridge100`. It is restricted to mitmproxy's IP and to ports 80/443.
- **IPv6 and QUIC rejected** to `<mitm_local>` (RST / ICMP unreachable): the container does not handle IPv6 and the `route-to` is TCP only. The browser immediately falls back to TCP over IPv4, which is intercepted. LAN clients also lose QUIC to these IPs (they go out via NAT on `en0`).
- **`<mitm_local>` table**: the daemon resolves the domains with `dscacheutil` (system resolver and cache, the same as the browser's) and keeps the IPs seen in the **last 15 minutes**: CloudFront (example.it) changes its set of IPs at every TTL expiry (60s), and the browser may use one obtained before the last resolution. Generated files: `/etc/pf.anchors/mitm.local` (current IPs) and `mitm.local.seen` (`<time of the last resolution> <IP> <domain>`). Thanks to the recorded domain, the IPs of a domain **removed from the list** leave the table immediately instead of after 15 minutes, and the daemon kills their states: the browser's already open connections drop and reopen without interception. IPs that have simply expired, instead, do not kill states. The table is **not** loaded by `pf.conf`: names are not resolved at boot (no network = failed load).
- **Container stop or IP change**: the daemon also kills the states to the table's IPs (`pfctl -k 0.0.0.0/0 -k <IP>`), so the browser's connections to the old container drop immediately instead of hanging.

Every name used by the site must be listed (`example.it` and `www.example.it` are distinct, no wildcards); resources on other domains (image CDNs, scripts) are not intercepted unless they are in the list.

**mitmproxy CA on the Mac**: `./mitmproxy/mitmproxy-ca-cert.pem`, to be added as trusted to the keychain (Safari and Chrome use the system one; Firefox has its own store, or `security.enterprise_roots.enabled`). Without it, the browser shows a certificate error on the listed domains. On an MDM-managed Mac, adding a root CA may be restricted by policy.

Check:
```bash
sudo pfctl -a com.apple/100.mitm.route -t mitm_local -T show
sudo pfctl -a com.apple/100.mitm.route -vsr
curl -sv -o /dev/null https://www.example.it/ 2>&1 | grep -i issuer
```
With interception active the issuer is `mitmproxy`, and the flow appears in mitmproxy (console or web UI) with the IP of `en0` as client. Today (without interception) it is `Amazon RSA 2048 M04`: Digital Guardian does not do TLS inspection on these connections.

### 11. Mocks: dashboard (`mockui/`) and addon (`scripts/mocks.py`)

Usage: [README.md](README.md#mocks). A mock replaces the response to the requests that match it, in the `request` hook, so the request **never reaches the server** (unlike the old `send_response.py`, which worked on `response`).

#### Why an addon, and not a mock server

Mockoon, WireMock and the like are mock servers to be reached at their own address. In transparent mode the clients' traffic cannot be diverted to them without **rewriting the destination**, which is exactly what this architecture avoids (`route-to` and not `rdr`, so that mitmproxy can recover the original address with `SO_ORIGINAL_DST`: section 2). The fake response therefore has to be injected into the flow by mitmproxy, i.e. by an addon. [`woltapp/mitmproxy-mock`](https://github.com/woltapp/mitmproxy-mock) does the same thing but is configured only by hand in JSON; a dashboard for the mocks is still an open request on mitmproxy's own web UI ([#7878](https://github.com/mitmproxy/mitmproxy/issues/7878)).

#### Two processes, one direction (almost)

The dashboard is a **separate process** in the same container, started by `entrypoint.sh`, not code inside the addon: this way the hot reload of the addons never has to release and reopen a socket, and an error in the dashboard does not touch the proxy. It uses `tornado`, already in the image as a dependency of mitmproxy (it is what mitmweb runs on), so **no new package** — the standard library is not enough, `cgi`, which parsed multipart uploads, was removed in Python 3.13.

```
browser on the Mac ──http://mitmproxy.test:8082──▶ mockui/server.py
                                                      │ writes
                                                      ▼
                            /mocks/enabled  +  /mocks/mocks.json  +  /mocks/files/
                                                      │ reads                volume ./mocks
                                                      ▼
                             mitmproxy + scripts/mocks.py ──▶ fake response in the flow
                                                      │ writes
                                                      ▼
                                           /mocks/hits.json (counters)
```

Every file has a **single writer** — `enabled` and `mocks.json` belong to the dashboard, `hits.json` to the addon — so there is no lock and no API between the two processes. Writes go through a temporary file and a rename, like the state files of `./mitm`: the reader never sees half a file. The addon rereads `mocks.json` when its mtime changes (one `stat` per request), so a change made from the dashboard, or by hand on the Mac, applies to the next request.

#### Copying a mock from a real request (`/mocks/ask`)

Usage: [README.md](README.md#mocks). The only thing the dashboard needs and cannot read from a file is the **flow history**, which lives in mitmproxy's memory. It asks the addon for it with the same request/answer pattern as `mac-editor.sh` towards the Mac, in `/mocks/ask`: each file still has a single writer.

```
browser ──GET /api/history[/<flow>]──▶ server.py ──writes──▶ ask/<token>.req
                                           │ waits (4s max)        │ reads (every 0.3s)
                                           ◀──reads── ask/<token>.res ◀──writes── scripts/mocks.py
                                                                            (mitmproxy's view addon)
```

- **Polling and not a socket**, for the same reason the dashboard is a separate process: a socket in the addon would have to be released and reopened at every hot reload. One listing of an almost always empty directory every 0.3s costs nothing; the exchange takes ~0.3s, the dashboard gives up after 4s (mitmproxy restarting, or the addon not loaded) and says so.
- **The source is the `view` addon**, i.e. exactly the flows the console or the web UI is showing, filter included — not a second copy recorded by the addon. Nothing is written to disk to keep a history.
- **The chosen request only fills the form**: the mock is created by the usual save, and `clean_mock` rebuilds it field by field as for any other. The match is method, host and path **without the query string** (every parameter of a real URL as a condition would make the mock match almost nothing); the response is the real one: status, `Content-Type`, the headers that are not rebuilt by `Response.make` (not `Content-Length`, `Content-Encoding`, hop-by-hop, `Date`, `Server`…) and the content.
- **Content only if it is text** and under 512 KB: a mock with a truncated body would be worse than one to fill in by hand. Text is decided by the `Content-Type`, not by the bytes: mitmproxy decodes a PNG into text without complaining (it falls back to an encoding that never fails).
- **What is left out is downloaded**: the dashboard shows an alert saying why, and when it is closed it downloads the real response (`/api/history/<flow>/body`), to be uploaded as the content of the mock. The addon writes the content next to its answer (`ask/<token>.body`) and the dashboard hands it to the browser and removes it: not inside the JSON answer (base64 of a few MB for every video), and nothing is kept on disk. What is written is the content, not the bytes on the wire — a gzipped file would be of no use.

#### The switch is not persisted

`/mocks/enabled` is an empty file whose mere existence means "mocks active". `server.py` **removes it when it starts**, so after every `./mitm start` the mocks are off until the switch in the UI is turned on. The container intercepts the traffic of the whole LAN: a mock left on from a previous session would be hard to diagnose. The same applies if the dashboard is restarted on its own.

#### Plain HTTP, and why

TLS with a certificate for `mitmproxy.test` issued by mitmproxy's own CA was tried and reverted: **Digital Guardian re-signs the browser's connections**, so the browser is handed a certificate issued by `Digital Guardian, Inc`, never ours, and marks it invalid — the extension cannot validate upstream a certificate signed by a root that lives in the user's keychain. From the terminal `curl` and `openssl` are not intercepted and saw the right certificate, which is what made the diagnosis slow (HISTORY, item 19). The same per-process filtering is the reason the whole project exists (*Why this approach*).

The loss is small: the dashboard is reachable only from the Mac over the container network, and no credentials travel on it.

#### Access only from the Mac

The dashboard listens on `0.0.0.0:8082` but rejects with `403` any connection whose source is not in the container network (`MITM_VM_NET`, passed by `entrypoint.sh`, which already computes it for the `iptables` rule). From the Mac the connections arrive through vmnet with a `192.168.64.0/24` source; LAN clients, which can reach the container (the Mac forwards `192.168.3.0/24` → `192.168.64.0/24`), are left out. Unlike the mitmweb UI, no password is needed.

#### Opening it from the console (key `M`)

The container cannot open a browser on the Mac. The `mock.dashboard` command reuses the `./edit` channel of `mac-editor.sh` (section 7): it writes `edit/mock-dashboard.url` with the URL and the request `edit/mock-dashboard.url.open` with the mode `url`, and the loop inside `./mitm open`/`attach` runs `open` on it — after checking that the URL is the dashboard's own, since it arrives from the container. If no terminal is attached, nobody claims the request: after 3s the addon removes it and prints the URL in the event log (`E`). If `open` fails on the Mac, the loop writes the reason in `edit/<file>.error` and the addon reports it in the same place — typically an attached session started before a change to `MOCK_URL`, which rejects the new address: detach and rerun `./mitm open`. Writing the request is retried through the event loop, never with a sleep: a file just removed on the Mac stays visible through the volume for about a second, and recreating it meanwhile fails with `ENOENT`. Outside the console there is `./mitm mock`.

## Known limitations / still to be verified

- **Mac traffic (section 10) tested only with `curl`**: with `example.com` added to `mac-domains.txt`, `curl https://example.com/` from the Mac responds with issuer `mitmproxy`, so `route-to`, anti-loop tag, REDIRECT in the container, mitmproxy egress and the return path to the IP of `en0` work. With the domain removed, the issuer goes back to the original one (Cloudflare) within ~15s. Still to be tested with a browser (Safari/Chrome, CA in the keychain), checking the counters of `pfctl -a com.apple/100.mitm.route -vsr` (the `route-to` rule on `en0` must count only the browser's connections).
- **Mac interception by IP, not by name**: CloudFront IPs are shared among many sites (the certificate of `www.example.it` is that of `www.lastampa.it`), so the traffic of other sites or apps that happen to use the same IPs is intercepted too. An app with certificate pinning on one of those IPs would fail. Possible fix: a mitmproxy addon that, for non-LAN clients, lets through without intercepting (`ignore_connection`) the connections whose SNI is not in the list.
- **Browsers with their own DNS** (Chrome/Firefox with DNS-over-HTTPS) may get IPs different from those resolved by the daemon: those connections are not intercepted.
- **Mac traffic on the default route**: the rules follow the interface of the default route (WiFi, Ethernet). With a VPN (`utun*`) as default route, that would become the WAN: NAT and `route-to` on `utun` are not tested.
- **Network change applied within 60s** (or immediately, if the system DNS changes): in the meantime the LAN clients' NAT and the Mac's rules stay on the previous WAN.

- **Mocks and QUIC**: what is not intercepted cannot be mocked either — QUIC on UDP 443 (see below) goes out via NAT without ever reaching mitmproxy.
- **Mock matching is by name, not by IP**: the host compared is the one in the request (`Host` header, thanks to `--showhost`). For the Mac's own traffic the IPs still have to be in `<mitm_local>`, i.e. the domain has to be in `mac-domains.txt`, otherwise the connection never reaches the container.
- **QUIC/HTTP3 on UDP 443** is not intercepted (`route-to`/`REDIRECT` are TCP only) and, since there is no rule blocking it, it goes out via NAT on `en0`. Clients such as Safari/Chrome on iOS may use it by default for many sites, with traffic bypassing mitmproxy without visible errors. To force the fallback to TCP, the following can be added to the `com.apple/100.mitm.route` rule in [daemon/mitm-pf-apply](daemon/mitm-pf-apply) (then `./mitm install`): `block in quick on en7 inet proto udp from 192.168.3.0/24 to any port 443`.
- **No DHCP between boot and login**: the `container` services run only in the user session, so DHCP starts at login (LaunchAgent, section 9), not at boot. Before login clients do not get/renew their lease. The pf daemon instead starts at boot and flushes the rules of the previous session.
- **Start at login tested only with `launchctl bootstrap`**, not yet with an actual logout/login or reboot.
- **`com.apple/100.mitm.*` anchors after a reboot still to be verified**: at boot they are empty and the daemon loads them (`RunAtLoad`). Only the live installation has been tested (NAT, DHCP, LAN and Mac interception); after the first reboot check `sudo pfctl -a com.apple/100.mitm.nat -sn` (two `nat` rules) and `sudo pfctl -vsA` (the old `com.mitm.*` must no longer appear).
- **The Mac is a single point of failure for the LAN**: with DHCP in relay mode, when the Mac is off or disconnected clients do not get/renew their lease and have no gateway. To go back to the standard setup: router in DHCP server mode (clients get gateway `192.168.3.1` back at the next renewal or on reconnecting).
- **DHCP renewals via relay to be verified over time**: the first lease through the Zyxel relay works (iPhone → `192.168.3.168`). It is not yet verified that the router also forwards unicast renewals addressed to `192.168.3.1`; if it did not, clients still renew via broadcast when T2 expires (~52 min with a 1h lease). To be checked in `container logs mitm-dhcp` after ~30 min (T1).
- **Clients' DNS tied to the Mac**: `192.168.3.2` is the only DNS offered. With `mitm-dhcp` stopped (`./mitm stop dhcp`, between boot and login) clients cannot resolve names, even if they still hold a valid lease.
- **LAN DNS to be tested on a real client**: verified `dnsmasq` → `192.168.64.1` (UDP and TCP, from `mitmproxy.test`), not yet the full path client → `192.168.3.2:53` → `rdr`. Clients holding the previous lease receive the new DNS at renewal (within ~30 min) or on reconnecting.
- **IPv6 and DNS**: if the router advertises an IPv6 DNS via RA (RDNSS), clients may use it instead of `192.168.3.2`, bypassing `dnsmasq`.
- **IPv6 not working** in the container network (plain timeouts) — not blocking for the current use (IPv4 traffic), but to keep in mind if IPv6 interception is needed in the future.
- **pf states after an IP change**: already open connections stay tied to the old container IP until the state expires; new ones use the updated rule.
- Duplicate rules in `iptables -t nat` at every entrypoint restart are handled with a preemptive `-F`, but it is worth checking over time that no leftovers accumulate elsewhere (e.g. if more chains are added in the future).
