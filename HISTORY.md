# History: problems diagnosed during construction

Problems encountered while building the system, in order, with cause and solution. The solutions described are the ones adopted at the time: the current state is in [ARCHITECTURE.md](ARCHITECTURE.md), which the "section N" references point to. File and anchor names are those of the time (e.g. `com.mitm.route`, now `com.apple/100.mitm.route`; `start-*.sh`/`stop-*.sh` scripts, now `./mitm`).

1. **macOS Application Firewall blocks mitmproxy listening on the Mac** → SYN never answered, centrally managed by MDM, cannot be changed from the CLI. Root cause of the decision to move mitmproxy into a container.
2. **`rdr` to `127.0.0.1` did not work** → suspected anti-spoofing on loopback for packets from an external source; solved (later superseded) by routing to the real IP/the container instead of loopback.
3. **`FileNotFoundError` in mitmproxy transparent mode inside the container** → caused by doing NAT on macOS (`rdr`) instead of inside the container: mitmproxy on Linux retrieves the original destination via `getsockopt(SO_ORIGINAL_DST)`, which requires the redirect to happen in the same kernel. Solved by switching to `route-to` (pf routes without translating) + `iptables REDIRECT` local to the container.
4. **Container did not stay running** → `iptables` failed for lack of the `NET_ADMIN` capability. Solved with `--cap-add NET_ADMIN`.
5. **Container IP cannot be fixed** → `--network` only supports `mac`/`mtu`, not `ip`. Solved with a script that reads the IP at runtime (`container inspect`) and regenerates the pf rule.
6. **`container inspect` failed when the whole script ran with `sudo`** → the `container` service is tied to the user session, not root. Solved by elevating only the commands that write to `/etc` and reload `pf`, not the whole script.
7. **Traffic not visible / hanging connections** → `route-to` pointed to the wrong interface (`en7` instead of the vmnet bridge `bridge100`) — the container is not reachable from `en7`. The script now derives the bridge from the container's gateway.
8. **Container egress timing out completely after enabling the REDIRECT** → solved by adding `-s 192.168.3.0/24` to the match. The exact cause is unclear: in netfilter `PREROUTING` does not see locally generated traffic, and incoming replies have *source* port 80/443, not destination port; the filter is correct anyway, since it limits the REDIRECT to LAN clients only.
9. **Dedicated `mitm-net` network not needed** → a network created with `container network create --subnet 192.168.70.0/24` gets its own bridge (not `bridge100`) and makes the subnet/gateway/interface of the `route-to` inconsistent. The `default` network is used.
10. **Old mitmproxy on Debian bookworm** → Python 3.11 ⇒ pip installs mitmproxy 11.0.2, without `web_password`. Solved with the `python:3.13-slim-bookworm` base image and a pinned version.
11. **Manual network configuration on the devices** → the router's DHCP does not allow a gateway other than itself. Solved with the router's DHCP relay towards the Mac + pf `rdr` + `dnsmasq` in a container (section 6), which assigns the Mac as gateway.
12. **DHCP container stopping right after start** → `dnsmasq` requires `NET_ADMIN` for DHCP. Solved with `--cap-add NET_ADMIN` on `mitm-dhcp` too.
13. **DHCP ok but the phone cannot browse** → mitmweb received the connections (`192.168.3.168`) but timed out towards every server (`Connect call failed … Errno 110`); from the container even `curl https://example.com` failed. Cause: the full reload of `/etc/pf.conf` (done to add `com.mitm.dhcp`) had removed the NAT anchors inserted at runtime by `InternetSharing` for `192.168.64.0/24`. Solved by adding `nat on en0 inet from 192.168.64.0/24 to any -> (en0)` to `com.mitm.nat` and reloading only that anchor (`pfctl -a com.mitm.nat -f …`). Alternative without pf: `container system stop` / `container system start` (then `./mitm start`), but the problem would come back at the next full reload.
14. **Web UI reachable only by typing the container IP** (which changes at every restart) → solved with the built-in DNS of `container` (`container system dns create test`). The first attempt resolved nothing (NXDOMAIN), even for containers created with `--dns-domain test`: the DNS only registers containers whose name is already `<name>.<domain>`. Container renamed from `mitm-proxy` to `mitmproxy.test`.
15. **After a reboot the phone could not browse and nothing restarted** → the `container` services do not register by themselves after a reboot, and `com.mitm.route` (now `com.apple/100.mitm.route`) still contained the `route-to` towards the container IP of the previous session (reloaded from `pf.conf` at boot). Solved with the `com.mitm.pf` LaunchDaemon (at boot it flushes the rules whose state files predate the boot) and the `com.mitm.dhcp` LaunchAgent (starts `container` and DHCP at login). The daemon also removes the scripts' `sudo` prompts.
16. **Public DNS servers not reachable on some networks** → clients received `1.1.1.1`/`1.0.0.1`, blocked on networks that only allow their own DNS servers; `dnsmasq` installed with brew on the Mac received nothing on port 53 (Application Firewall). Solved by enabling DNS in the same `dnsmasq` instance as DHCP, with pf `rdr` `192.168.3.2:53` → container and upstream `192.168.64.1` (the Mac's resolver, hence the DNS servers of `en0`). Clients are offered only `192.168.3.2`.
17. **Manual setup of `/etc/pf.conf`** (modified copy with the `com.mitm.*` anchors, full reload that removed the `InternetSharing` anchors, DHCP anchor file to be created before loading) → not portable to another Mac and at risk of being reverted by macOS updates. Solved by moving the rules into child anchors of `com.apple` (`com.apple/100.mitm.*`), already reached by the system `/etc/pf.conf`, generated and loaded by the daemon, also at boot (section 2). Order verified with test rules: `100.*` takes precedence over `300.*` for filtering and `rdr`, and the NAT in `100.*` is applied.
